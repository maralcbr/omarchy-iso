# 4.0.3 platform preparation

Base: aurora/rc-channel at cc8c513. This branch prepares local Asahi and Aurora
payloads for the paired 4.0.3 runtime, without changing public channels.

- Refresh the 18-package Asahi snapshot from the vendor aarch64 release.
  Package contents, SHA-256 checksums and detached signatures were verified
  against the existing pinned signing key. The trust key is unchanged.
- Advance Linux Asahi from 7.1.6.asahi1-1 to 7.1.13.asahi1-1 and U-Boot from
  2026.04.asahi2-1 to 2026.07.asahi2-1. Retain Aurora 7.1.12.aurora2-1.
- Reassemble both boot images from m1n1, the corresponding kernel device trees,
  and the new U-Boot gzip stream. Updating shared U-Boot changes both image
  hashes even though the Aurora kernel stays fixed. Verify the exact logo
  regions before deriving each branded output and updating product pins.
- Reserve September 10 payload filenames. Existing artifact and release
  directories in the primary checkout are not modified.

valid database entries, but extra.db has a corrupt findnewest-0.3-4/desc entry
filled with zero bytes. The rsync copy, direct HTTPS download, and GeoIP

42c79058c47f6952ffca503e2b8419d4d8c4904c8d08e7863578c2717070d4b5.
The new snapshot is not accepted or published. Keep the existing 20260906
configuration until this defect is resolved and the snapshot reverified.

## Payload gate

The ARM repository/runtime descriptor pins still name the previous signed
candidate. Replace all fields together with the verified 4.0.3 candidate
identity after authorized source landing and candidate publication. Never run
a payload build with the old runtime pins and call it a 4.0.3 image.

Before M1 installation, require candidate-bound VM evidence, a locally
qualified full payload, correct installer metadata, and the identified M1
Omarchy partition layout. Preserve macOS. No physical or public release
readiness is claimed by these source changes.
